# 评测基准与脚本

HallucC 有两套互相独立、针对不同检测层的评测体系：

| 体系 | 检测对象 | 数据集 | 核心脚本 | 关键指标 |
|---|---|---|---|---|
| **文本级幻觉评测** | 一段文本中的声明（claim）是否被正确判定为 refuted / supported / unverified | `eval_set/chinese_hallucination_benchmark.jsonl`（规范集）+ `samples*.json`（运行集） | `eval.py` / `run.py` / `run_eval_domain.py` | recall（漏报控制）、fp_rate（误报率）、延迟 |
| **Agent 轨迹幻觉基准** | 一条 Agent 执行轨迹中的失败模式是否被正确检出 | `agent_benchmark.py::BENCHMARK_CASES`（20 条植入轨迹） | `agent_benchmark.py` / `agent_pipeline.evaluate_trajectory` | recall、fp_rate、precision、F1、实例级 recall/precision、每模式检出率 |

两者均支持 **fast 档离线评测**（零 LLM / 零搜索调用），便于在不消耗 API 额度的情况下回归验证。

## 一、文本级幻觉评测

### 1.1 数据集

#### 1.1.1 规范集：`eval_set/chinese_hallucination_benchmark.jsonl`

中文幻觉检测基准，v1.0，CC-BY 4.0。文件为首行带 `#` 注释的 JSONL，每行一条样本。

**Schema：**

```jsonc
{
  "id": "eval_001",
  "category": "编造事实",
  "text": "DeepSeek 是由阿里巴巴成立的通用人工智能公司……",
  "claims": [
    {"text": "DeepSeek 是由阿里巴巴成立的", "expected_status": "refuted", "note": "由幻方量化创立"},
    {"expected_status": "supported", "text": "……", "note": "……"}
  ]
}
```

- **样本数**：100 条
- **声明数**：175 条
- **声明状态分布**：refuted 124 / supported 36 / unverified 15
- **9 个类别**：编造事实(24)、张冠李戴(14)、数据错误(14)、时间错误(12)、地点错误(10)、人名错误(8)、引用捏造(6)、逻辑矛盾(6)、过度推断(6)
- 配套数据卡：`eval_set/README.md`

> ⚠️ **注意：`eval_set/README.md` 中的数字与样本/声明计数有出入**（README 称「约 260 条声明、180 refuted / 50 supported / 30 unverified」，实测为 175 条、124/36/15）。以本文档与实际文件为准。

#### 1.1.2 运行集：`samples*.json`（legacy）

`eval.py` 实际加载的样本集，根目录下共 5 个：

| 文件 | 样本数 | 用途 |
|---|---|---|
| `samples.json` | 32 | 默认通用集（`HALLUC_SAMPLES` 未设时） |
| `samples_fact.json` | 16 | `run_eval_domain.py general` 指向 |
| `samples_medical.json` | 8 | 医疗领域 |
| `samples_legal.json` | 8 | 法律领域 |
| `samples_finance.json` | 8 | 金融领域 |

**Schema（与规范集不同）：**

```jsonc
{
  "id": "...",
  "category": "...",
  "text": "...",
  "claims_expected": [
    {"contains": "字节跳动", "expected_status": "refuted"}
  ]
}
```

#### 1.1.3 ⚠️ Schema 差异（重要）

两套数据集字段名不一致：

| | 规范集 `eval_set/*.jsonl` | 运行集 `samples*.json` |
|---|---|---|
| 声明数组键 | `claims` | `claims_expected` |
| 声明文本键 | `text` | `contains` |
| 备注 | 有 `note` | 无 `note` |

`eval.py` 的 `_align()` 按 **`claims_expected` / `contains`** 读取（见 §1.2），因此：

- `eval.py` **可直接消费** `samples*.json`；
- `eval.py` **不能直接对齐** `eval_set/chinese_hallucination_benchmark.jsonl` —— 需要一个字段适配器把 `claims→claims_expected`、`text→contains`（二者语义一致：`contains` 是用于子串匹配的针，`text` 是完整声明文本，将 `text` 作为 `contains` 即可对齐）。

`eval_set/README.md` 给出的用法示例 `python eval.py --dataset ...` 是**不准确的**：`eval.py` 没有 `--dataset` 参数。当前正确做法是用 `HALLUC_SAMPLES` 环境变量指定样本文件（见 §1.5）。

### 1.2 评测脚本

#### `eval.py`（核心评测框架）

| 函数 | 作用 |
|---|---|
| `load_samples(path)` | 加载样本；`path` 默认取环境变量 `HALLUC_SAMPLES`，否则回退 `samples.json` |
| `_align(claims_expected, detected_claims)` | 把「期望标签」与「检测器检出的声明」对齐：用 `contains` 做子串匹配；**refuted 期望优先匹配 refuted 检出**，未匹配到的 refuted 回退为「是否存在 red 检出」 |
| `run_eval()` | 跑全集：逐样本打印 red/yellow/green 分布 + 延迟，汇总 recall / fp_rate |
| `run_eval_domain(domain)` | 领域评测：`domain_override.set(domain)` 切换领域画像后跑全集 |
| `run_single(text)` | 单文本检测，返回完整结构化 JSON |

**声明级别（claim level）：**

| 级别 | 判定条件 |
|---|---|
| 🔴 red | `refuted` 且置信度 ≥ 0.8 |
| 🟡 yellow | `unverified` / 不确定 |
| 🟢 green | `supported` |

**核心指标：**

- **recall（漏报控制）** = 期望为 refuted 的声明中，被检出为 red 的比例。recall 越高，漏报越少。
- **fp_rate（误报率）** = 期望为 supported 的声明中，被误判为 red 的比例。越低越好。
- **决策门槛**：recall 高 **且** fp_rate < 30% 视为通过。

> 项目约定（见 CLAUDE.md）：`unverified` 是弃权，不否决实质性投票；证据不足 → `unverified`，绝不强行判 `refuted`。这是控制误报的核心策略。

#### `run.py`（CLI 入口）

```bash
python run.py            # 跑 run_eval()（默认 samples.json）
python run.py "某段文本"  # 跑 run_single(text)，单文本结构化输出
```

`RUN_MODE` 环境变量控制是否走真实 API（见 §1.3）。

#### `run_eval_domain.py`（领域 CLI）

```bash
python run_eval_domain.py medical   # samples_medical.json + 医疗画像
python run_eval_domain.py legal     # samples_legal.json + 法律画像
python run_eval_domain.py finance   # samples_finance.json + 金融画像
python run_eval_domain.py general   # samples_fact.json + 通用画像
```

原理：设置 `HALLUC_SAMPLES=samples_<domain>.json`（general → `samples_fact.json`），并 `domain_override.set(domain)` 切换领域画像（`domains.py` 提供各领域 prompt 提示与可信源域名）。

#### `tests/test_eval.py`

用 `MockClaimResult` 数据类（`.level` 属性：refuted+conf≥0.8→red、supported→green、else yellow）对 `_align` 的对齐逻辑做 7 组单元测试，覆盖 refuted 优先匹配、未匹配回退、误报统计等路径。

### 1.3 运行模式（`RUN_MODE`）

| Mode | 行为 |
|---|---|
| `mock` | 不调用任何外部 API，确定性假数据，用于流程验证（**默认**） |
| `real` | 真实 DeepSeek + 千度/必应搜索 |
| `record` | 真实搜索 + 把结果按 query 哈希写入 `fixtures/`（评测录制） |
| `replay` | 只读 `fixtures/`，绝不联网（**零额度重跑**，用于 prompt 迭代） |

`fixture_search.py::FixtureSearch(mode)` 实现 record / replay：

- `_query_hash(query)` → 查询指纹；
- `_path()` → `fixtures/` 目录下按哈希命名的缓存文件；
- `search(query, top_k)` → record 写入、replay 读出；
- **只缓存非空结果**（临时失败 ≠ 无结果，避免污染缓存）——见 CLAUDE.md「Fixture cache」约定。

### 1.4 领域评测

- `config.domain_override`（`ContextVar`）承载当前领域（general / medical / legal / finance）；
- `domains.py` 定义各领域画像：专用 prompt 提示、可信源域名白名单等；
- `run_eval_domain.py` 是 CLI 封装（见 §1.2）。

### 1.5 运行示例

```bash
# 1. mock 模式快速验证流程（无需任何 key）
RUN_MODE=mock python run.py

# 2. 真实模式跑全集
RUN_MODE=real python run.py

# 3. 录制搜索结果到 fixtures/（一次性，消耗额度）
RUN_MODE=record python run.py

# 4. 零额度重跑（迭代 prompt 时反复用，0 搜索成本）
RUN_MODE=replay python run.py

# 5. 领域评测
RUN_MODE=real python run_eval_domain.py medical

# 6. 单文本结构化输出
RUN_MODE=mock python run.py "DeepSeek 是由阿里巴巴成立的"

# 7. 对规范集 eval_set/*.jsonl 跑评测（需先做字段适配，见 §1.1.3）
#    eval.py 无 --dataset 参数；用 HALLUC_SAMPLES 指向适配后的文件：
#    HALLUC_SAMPLES=eval_set/_adapted.json RUN_MODE=replay python run.py
```

## 二、Agent 轨迹幻觉基准（HallucC-Agent-Bench）

### 2.1 设计原则

1. **植入式真值（planted ground truth）**：每条幻觉轨迹的失败模式是**按各确定性探测器的精确触发条件手工植入**的，而非由检测器自身输出反推 —— 避免同义反复（tautology）。
2. **诚实的覆盖缺口**：明确声明 fast 档不覆盖哪些失败模式（`COVERAGE_GAP`），不假装全覆盖。
3. **fast 档零成本**：fast 档 0 次 LLM 调用、0 次搜索调用，确定性规则层，便于 CI 回归。

### 2.2 数据集：`BENCHMARK_CASES`

`agent_benchmark.py::_build_cases()` 在内存中构建 20 条 `BenchmarkCase`：

- **8 条 clean**（`label="clean"`，`expected_failure_modes=[]`）：c1–c8
- **12 条 hallucinated**（`label="hallucinated"`）：h1–h12，共植入 16 个 `(code, step)` 实例

**`BenchmarkCase` 结构：**

```python
BenchmarkCase(
    id="h11_multi_mode",
    task="查询订单",
    trajectory=[{
        "step": 1,
        "action": "query_db",        # 不在注册表 → HALLUCINATED_TOOL
        "action_input": '{"id":"1234567"}',  # 刚性 ID 无来源 → PARAM_FABRICATION
        "observation": "失败",        # 失败 obs
        "agent_claim": "查询成功找到3条",  # 声称成功 + 与 obs 不相似
    }],
    label="hallucinated",
    expected_failure_modes=[
        ("HALLUCINATED_TOOL", 1),
        ("PARAM_FABRICATION", 1),
        ("OBSERVATION_IGNORED", 1),
        ("CLAIM_MISMATCH", 1),
    ],
    note="「厨房水槽」用例：单步同时触发 4 种失败模式",
)
```

**轨迹 step 字段**：`step`、`action`、`action_input`、`observation`、`agent_claim` / `final_answer`。

**注册工具集 `TOOL_SCHEMAS`（5 个）：** `search`、`lookup_order`、`calculator`、`translate`、`get_weather`。不在该集合的 `action` → `HALLUCINATED_TOOL`。

#### 8 条 clean 轨迹

| id | task | 设计要点（为何不触发任何探测器） |
|---|---|---|
| c1_weather | 查询北京天气 | obs=claim |
| c2_order | 查询订单 1234567 | 刚性 ID 放进 task（有来源）+ claim=obs |
| c3_calc | 计算 123+456 | 算式核验通过；数字 <5 位非刚性 ID |
| c4_search | 搜索 HallucC | claim=obs |
| c5_multistep | 查天气并翻译 | 多步、不同 obs 不触发 redundant |
| c6_empty_result | 搜索稀有资料 | 空结果但 claim 如实转述（含「未找到」失败标记） |
| c7_translate | 翻译「你好」 | claim=obs |
| c8_final_answer | 今天北京天气 | 用 `final_answer` 字段，normalize 后 claim=obs |

#### 12 条 hallucinated 轨迹

| id | task | 植入的失败模式 `(code, step)` | 触发原理 |
|---|---|---|---|
| h1_hallucinated_tool | 查询数据库 | HALLUCINATED_TOOL@1 | `action=query_database` 不在注册表 |
| h2_schema_violation | 查询天气 | SCHEMA_VIOLATION@1 | `get_weather` 缺必填 `city` |
| h3_claim_mismatch | 搜索数据 | CLAIM_MISMATCH@1 | obs「5条」vs claim「50条」，token-Jaccard<0.5 |
| h4_observation_ignored | 发通知 | OBSERVATION_IGNORED@1, CLAIM_MISMATCH@1 | obs 失败却声称成功；两信号同源 |
| h5_overconfident_assertion | 分析市场地位 | OVERCONFIDENT_ASSERTION@1 | 占比 150% >100%；obs=claim 隔离掉 CLAIM_MISMATCH |
| h6_param_fabrication | 查询订单状态 | PARAM_FABRICATION@1 | 刚性 ID 在 task/前序无来源；claim 空避免误触其他 |
| h7_loop | 搜索资料 | LOOP@2 | 同 (action, action_input[:50]) 重复 |
| h8_retry_storm | 搜索 | RETRY_STORM@3 | 同 action ≥3 不同入参且含失败 obs |
| h9_redundant_step | 查天气 | REDUNDANT_STEP@2 | 不同调用但 obs 相似度=1.0 |
| h10_handoff_loss | 查询数据 | HANDOFF_LOSS@2 | 后续 claim 含纠正标记「实际为」「并非」+与前序相似≥0.4 |
| h11_multi_mode | 查询订单 | HALLUCINATED_TOOL@1, PARAM_FABRICATION@1, OBSERVATION_IGNORED@1, CLAIM_MISMATCH@1 | 单步「厨房水槽」触发 4 种 |
| h12_math_error | 计算 10+20 | CLAIM_MISMATCH@1 | 算式 10+20=30 声称 40，math_checker 核验不符 |

### 2.3 失败模式

`failure_mode_codes.FAILURE_MODE_CODES` 定义 12 个失败模式码（`annotation.py` 再导出以向后兼容 `from annotation import …`）：

| Code | 含义 | fast 档覆盖 |
|---|---|---|
| HALLUCINATED_TOOL | 调用了不在注册表中的工具 | ✅ |
| PARAM_FABRICATION | 刚性 ID 参数凭空捏造（task/前序无来源） | ✅ |
| SCHEMA_VIOLATION | 缺必填参数 / 类型不符 | ✅ |
| OBSERVATION_IGNORED | obs 含失败标记却声称成功 | ✅ |
| CLAIM_MISMATCH | claim 与 obs token-Jaccard<0.5，或算式不符 | ✅ |
| LOOP | 同 (action, input) 重复 | ✅ |
| RETRY_STORM | 同 action ≥3 不同入参且含失败 obs | ✅ |
| REDUNDANT_STEP | 不同调用但 obs 相似度≥0.8 | ✅ |
| HANDOFF_LOSS | 后续 claim 纠正前序 claim（nli 缺省走相似度回退） | ✅ |
| OVERCONFIDENT_ASSERTION | 常识矛盾（>100% 占比 / 日期悖论） | ✅ |
| **SCOPE_DRIFT** | 范围漂移 | ❌ 仅 LLM 档 |
| **PREMATURE_STOP** | 过早终止 | ❌ 仅 LLM 档 |

**覆盖缺口 `COVERAGE_GAP = ("SCOPE_DRIFT", "PREMATURE_STOP")`**：这两个模式依赖语义判断，仅 standard/deep（LLM）档覆盖；fast 档（纯规则层）不覆盖，因此基准中也未植入这两种实例。

### 2.4 评测脚本

#### `agent_benchmark.py`

| 符号 | 作用 |
|---|---|
| `BenchmarkCase` / `CaseResult` / `BenchmarkReport` | 数据类 |
| `BENCHMARK_CASES = _build_cases()` | 20 条基准轨迹 |
| `run_benchmark(speed="fast", cases=None)` → `BenchmarkReport` | 跑全集 |
| `_run_one(case, speed)` → `CaseResult` | 跑单条 |
| `main(speed="fast")` | CLI 入口，打印 summary |
| `ACCEPT_RECALL = 0.80` | recall 验收门槛 |
| `ACCEPT_FP_RATE = 0.15` | fp_rate 验收门槛 |
| `COVERAGE_GAP` | fast 档不覆盖的模式（见 §2.3） |

#### `agent_pipeline.evaluate_trajectory(...)`

```python
evaluate_trajectory(
    trajectory, tool_schemas, speed="standard", ...,
    max_llm_calls=60,
) -> AgentPipelineResult
```

`AgentPipelineResult` 字段：`speed`、`failure_modes`（`[{code, step}]` 列表）、`llm_calls`、`search_calls`、`dimensions`、`propagation`。

- **speed="fast"**：仅跑 `_rule_layer`（结构化 + failure_modes 探测器），**0 LLM / 0 搜索**；
- **speed="standard"/"deep"**：在规则层之上叠加 LLM 层（覆盖 `COVERAGE_GAP` 中的语义模式）。

#### `agent_eval.evaluate(...)` — 规则引擎（最底层）

`agent_pipeline._rule_layer` 调用的最底层确定性评估器，**纯 stdlib、0 LLM**：六维评分 + 工具 Schema 校验 + 观察↔声称相似度 + 循环检测。`failure_modes.py` 的 5 个补充探测器与 `common_sense._is_obviously_false`（`OVERCONFIDENT_ASSERTION`）在其之上叠加（见 `agent_pipeline._rule_layer` L179-183）。

```python
evaluate(trajectory, tool_schemas=None) -> AgentEvalResult
```

| 符号 | 作用 |
|---|---|
| `evaluate(trajectory, tool_schemas=None)` → `AgentEvalResult` | 六维量化 + 逐 步 checks + 4 个失败模式码 |
| `_normalize_step(s, idx)` | 归一两种 step schema 到统一内部表示（见下表），使 `/detect-agent` 与 `/detect-agent-trajectory` 两端点 + CLI 共用同一评估器 |
| `_validate_schema(action_input, schema)` → `(ok, detail)` | JSON Schema 校验：必填项 + 类型（string/number/integer/boolean） |
| `_text_similarity(a, b)` → `0-1` | token overlap（中文按字 / 英文按词）+ bigram Jaccard |
| `CLAIM_MISMATCH_THRESHOLD = 0.5` | observation vs agent_claim 相似度低于此 → `CLAIM_MISMATCH` |

**双 schema 容忍（`_normalize_step`）：**

| | schema A（`/detect-agent`） | schema B（`/detect-agent-trajectory`） |
|---|---|---|
| 工具/动作 | `tool` | `action` |
| 入参 | `tool_input` | `action_input` |
| 输出 | `tool_output` | `observation` |
| 声称 | `agent_claim` | `final_answer`（回退 `agent_claim`） |

**`tool_schemas=None` 的优雅降级**：`HALLUCINATED_TOOL`（L163 `if tool_schemas and action`）与 `SCHEMA_VIOLATION`（L175 `if tool_schemas and action in tool_schemas`）均以 `tool_schemas` 为前提；传 `None` 时**跳过这两类检测但不崩溃**——这是 `halluc-detect detect` 默认不传 `tool_schemas` 的契约基础（避免用户自定义工具被误判 `HALLUCINATED_TOOL`），`--tools demo` 才加载基准 5 工具注册表。

**`AgentEvalResult`：**

- `to_dict()` → **6 个 float**（`tool_correctness` / `argument_correctness` / `output_faithfulness` / `step_efficiency` / `loop_detection` / `propagation_score`），向后兼容（`tests/test_todays_features.py:61` 断言 `len==6`）；
- `structured()` → `{dimensions{4 维 score+confidence}, steps[].checks[], failure_modes[]}`；`reasoning_coherence` / `task_completion` 两维需 LLM 裁判，由 `agent_pipeline` 在 standard/deep 档补全后并入。

**直接发出的失败模式码（4 个）：**`HALLUCINATED_TOOL`、`SCHEMA_VIOLATION`、`CLAIM_MISMATCH`、`LOOP`。其余确定性码（`PARAM_FABRICATION` / `OBSERVATION_IGNORED` / `RETRY_STORM` / `REDUNDANT_STEP` / `HANDOFF_LOSS` 在 `failure_modes.py`，`OVERCONFIDENT_ASSERTION` 在 `common_sense`）由 `agent_pipeline._rule_layer` 在 `evaluate()` 之上叠加。

#### 指标体系

`BenchmarkReport` 同时给出两套指标：

**Case 级（按轨迹判定是否含幻觉）：**

| 指标 | 定义 |
|---|---|
| TP / FN / FP / TN | 幻觉轨迹被正确判幻觉 / 漏判 / clean 被误判 / clean 正确 |
| accuracy | (TP+TN)/total |
| recall | TP/(TP+FN)（漏报控制） |
| precision | TP/(TP+FP) |
| F1 | 调和平均 |
| fp_rate | FP/(FP+TN)（误报率） |

**实例级（按 `(code, step)` 对齐，更严格）：**

| 指标 | 定义 |
|---|---|
| inst_tp / inst_fn / inst_fp | 植入实例被正确检出 / 漏检 / 误报 |
| inst_recall / inst_precision | 实例级召回 / 精确率 |

外加 **每个失败模式的检出率**（`per_code_detection`，如 `CLAIM_MISMATCH 4/4 = 1.0`）。

**验收门槛（P2）：** `recall ≥ 0.80` 且 `fp_rate ≤ 0.15`。

#### 当前 fast 档实测（planted 基准）

```
TP=12  FN=0  FP=0  TN=8
accuracy=1.0  recall=1.0  precision=1.0  F1=1.0  fp_rate=0.0
inst: TP=16  FN=0  FP=0  → inst_recall=1.0  inst_precision=1.0
成本: llm_calls=0  search_calls=0
```

> 这是植入式基准的预期结果：规则探测器对自身精确触发条件构造的用例应全检出、无误报。它验证的是**探测器实现与触发条件文档的一致性**，而非对真实分布的泛化能力——后者需用真实轨迹另行评测。

## 四、已知限制与注意事项

1. **规范集 ↔ eval.py 不直接兼容**（§1.1.3）：`eval_set/*.jsonl` 用 `claims/text`，`eval.py::_align` 读 `claims_expected/contains`。跑规范集需字段适配；当前 `eval.py` 也无 `--dataset` 参数，需用 `HALLUC_SAMPLES` 指向适配后的文件。
2. **`eval_set/README.md` 计数不准**（§1.1.1）：声明总数与状态分布以实际文件为准（175 条；refuted 124 / supported 36 / unverified 15）。
3. **Agent 基准测的是「实现一致性」而非「泛化」**（§2.4）：planted 基准上满分验证的是规则探测器与其触发条件文档一致；对真实 Agent 轨迹的泛化能力需另行采集真实数据评估。
4. **fast 档有覆盖缺口**（§2.3）：`SCOPE_DRIFT`、`PREMATURE_STOP` 仅 LLM 档覆盖；fast 回归不等价于全模式通过。
5. **两套体系独立**：文本级评测针对声明判定质量，Agent 基准针对轨迹失败模式检出，二者指标不可混用。
